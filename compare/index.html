0. 一句话结论

五个「不同」的系统，玩的是同一套 52 个玩法。

b-stargather、c-shule、d-siixun 三家的玩法 JS 52 个文件、52 个字节级完全相同；

a-choujiang 改了 8 个（44 个相同），e-import-games 改了 6 个（46 个相同）。

真正的差异在外壳：后端语言、后台形态、部署方式。玩法层是全行业共用的一份。

2. 玩法库同源（核心发现）

五个仓里 screen*.js 的命名完全一致，各 52 个，且都放在 static/js/screenjs/ 这一层：

screencore.js  screenjumprace.js  screenmls.js  screenxxx.js ...

两两比对（同名文件内容 MD5）：

对比同名文件内容完全相同
b-stargather ↔ c-shule5252
b-stargather ↔ d-siixun5252
c-shule ↔ d-siixun5252
a-choujiang ↔ d-siixun5244
a-choujiang ↔ e-import-games5249
b-stargather ↔ e-import-games5246

怎么读这张表：

  • b / c / d 三家是同一份代码的三个副本，一个字都没改。
  • a-choujiang 改动了 8 个玩法（screencore.js 30,373 B vs 原版 29,323 B，说明它动过引擎核心）。
  • e-import-games 改了 6 个，属于"复原过程中修补"。
  • 玩法命名（screenjumprace / screenmls …）是思讯（d-siixun）的命名风格，说明这份库的源头就是 d。

推论： 谁号称"自己有 50 多个玩法"，实际竞争壁垒都不在玩法，而在后台、账号体系、结算和部署。

4. 各自的真实形态

仓形态技术栈证据能独立跑吗适合谁
a-choujiang自研全栈大屏系统（Go 后端 + Vue 后台 + 55 个玩法页）go.mod、Vue SPA、C++ 大屏播放器需要 Go 环境 + 数据库想自建、能读 Go 的团队
b-stargather商业成品：42 个服务端插件 + 桌面端（含 Electron）package.json、42 个 plugins/*（每插件一条业务线）需要 Node 环境开箱交付，插件式扩展
c-shule整站镜像（858 个 html，多域名多份拷贝）无工程文件，纯静态起个静态服务器就能看学界面/抄页面，不能当产品
d-siixun原版玩法与素材库无工程文件只能当"大屏运行时"当参考基准，验证别的仓改了啥
e-import-games三版复原实验（v1 完整复原 / v2 / 像素级独立版）requirements.txt + Python 工具链需要 Python做"导入/还原"工具的场景

5. 数据里挖出来的三个坑

  1. 仓库体积不能当工作量看：.git 占 26%–49%。b 有 2.3 GB，但去重后源码 34.6 万行，比 a 还少 7 万行。
  2. c-shule 有套娃副本：hd.shulehudong.com/ 里面又套了一层 hd.shulehudong.com/，所以它 206 个 screen*.js 去重后只剩 52 个。整站被复制了两份。
  3. d-siixun README 说"97 个玩法"，本轮复现不出来：实测命名规范可点的只有 52 个 screen*.js；E-互动生产版/js 另有 135 个 webpack 混淆 chunk，里面可能还藏着别的玩法，但没有可读证据。口径存疑，未采信。

8. 本轮测量的局限（别当成全知）

  • 判定同源用的是文件名 + MD5，只能证明"这份文件没动过"，不能证明"没有别处另写的实现"。
  • 行数统计排除了平均行长 >300 字符的压缩文件，所以混淆过的 135 个 chunk 不计入 —— 也就是说 b/c 的真实业务量可能被低估。
  • a 的 48,014 行 C++ 来源未确认，可能是第三方播放器/解码库，不能直接算它"自研"。
  • 玩法数 52 是"能按命名规则识别出的大屏玩法"，不含后台活动、签到、投票等其它玩法形态。
